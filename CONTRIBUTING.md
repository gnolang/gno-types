# Contributing to `@gnolang/gno-types`

Thanks for your interest in contributing! This document covers the bits that aren't obvious from the code — primarily how the types are generated and our release flow.

## Development setup

```bash
pnpm install
pnpm build
pnpm lint
```

## Regenerating types

The TypeScript sources under `src/` are generated from the `.proto` files under `protos/` with [`ts-proto`](https://github.com/stephenh/ts-proto). Do not edit them by hand.

```bash
pnpm codegen
```

This requires `protoc` to be installed and available on your `PATH`.

Only the protos under the `ROOTS` listed in `scripts/generate.sh` (`gno`, `ibc`, `tendermint`, `tm`) are generated; `ts-proto` also emits every proto they import. The other directories under `protos/` (`cosmos`, `gogoproto`, `google`, ...) hold just those dependencies, so when adding a proto, copy in only the files it imports.

The gno protos under `protos/gno/` mirror the amino-generated protos in the [gno repository](https://github.com/gnolang/gno) (e.g. `tm2/pkg/std/std.proto`, `gno.land/pkg/sdk/vm/vm.proto`), adapted to this package's proto packages and friendlier message names (e.g. `m_call` → `MsgCall`). When syncing with gno, keep field numbers and types identical to upstream.

## Releasing: Changesets

Versioning, changelog generation, git tagging, and npm publishing are all driven by [Changesets](https://github.com/changesets/changesets). You should not edit `CHANGELOG.md`, bump the version in `package.json`, or run `npm publish` by hand.

### Adding a changeset to your PR

Any PR that affects the published package must include a changeset. PRs that only touch internal tooling (CI, contributor docs) do not need one.

From the repo root:

```bash
pnpm changeset
```

The CLI will prompt you to:

1. Pick a bump type — `patch` for bug fixes, `minor` for backwards-compatible features (e.g. new messages or fields), `major` for breaking changes (e.g. renamed or removed messages). Follow [Semantic Versioning](https://semver.org/).
2. Write a short summary. The summary becomes the bullet point in the published changelog, so write it for end users — describe the user-facing change, not the implementation. Markdown is supported.

This creates a Markdown file under `.changeset/` (e.g. `.changeset/quiet-pandas-jump.md`). Commit it as part of your PR.

If you forget, you can also create the file manually:

```markdown
---
"@gnolang/gno-types": patch
---

Short, user-facing description of the change.
```

### How releases happen

The `Release` GitHub Actions workflow (`.github/workflows/release.yaml`) runs on every push to `main`:

- **If there are pending changesets in `.changeset/`**, the workflow opens (or updates) a PR titled **"chore: version packages"**. That PR consumes the changesets, bumps `package.json`, and writes the new entries into `CHANGELOG.md`.
- **When that PR is merged**, the workflow runs again, sees no pending changesets, and instead builds the package, publishes it to npm, and pushes a git tag for the new version.

In short: **you write the changeset, the bot does the rest.** Maintainers review the version PR like any other PR before merging.

### Useful local commands

```bash
# Add a changeset interactively
pnpm changeset

# See which changesets are pending and what version bump they imply
pnpm changeset:status

# Apply pending changesets locally (bumps package.json, updates CHANGELOG.md, deletes consumed changesets).
# You normally don't run this manually — the release workflow does it via the version PR.
pnpm version:packages

# Build and publish to npm. Also bot-only in normal flow.
pnpm release
```

### npm publishing

The release workflow publishes with npm [trusted publishing](https://docs.npmjs.com/trusted-publishers) (OIDC) and provenance, so no npm token is stored in the repository. `@gnolang/gno-types` must have `gnolang/gno-types` with the `release.yaml` workflow configured as a trusted publisher on npmjs.com. `GITHUB_TOKEN` is provided automatically.

### Pre-changesets history

Versions `1.0.0` through `1.0.8` predate this workflow and were released manually. From the next release onward, the changelog is generated by Changesets.

## Pull requests

- Keep PRs focused — one logical change per PR.
- Run `pnpm lint` and `pnpm build` before pushing.
- Include a changeset (see above) unless your change does not affect published output.
